# 后台改稿后，如何继续修改

用户在公众号后台改过文章时，后台版本作为下一次修改的起点。先拉回、保留快照，在副本上做最小修改，再检查后台是否被别人继续改动。不要重新建一篇草稿，也不要用本地旧稿覆盖后台。

## 支持范围

自动入口 `scripts/draft_sync_guarded.py` 只处理已建立拉回基线的普通单篇、正文单图草稿。多篇消息组、多图、复杂 Word/贴图 HTML 不适用，遇到时保留文件、引导人工编辑；不能降成单图偷偷丢内容。`tools/draft_sync.py` 是内部依赖，不绕过守卫调用更新。

命令中 `SKILL_DIR` 与 `ARTICLE_DIR` 分别替换为已经核对的技能安装绝对路径与文章绝对路径。脚本能否联网与是否保存文件要分别取得对应范围授权，不让小白自己猜目录。

## 1. 拉回并留基线

用户已经说“拉回我后台改过的这篇”即为这次读取授权，不用重复确认。核对对应文章和草稿标识后：

```text
python "<SKILL_DIR>/scripts/draft_sync_guarded.py" pull --article-dir "<ARTICLE_DIR>" --approve-read
```

必要时按帮助提供 `--media-id`，不要凭标题猜另一篇。拉回文件保存在本篇 `sync/`；秘密凭据来自本机私有环境变量，不读取其他工具留下的 token。快照应唯一命名，保留 `sync/state.json` 中的基线信息，不能手工伪造。

## 2. 在拉回稿的副本上修改

保留原 HTML 快照，在本篇目录内的副本上最小修改；不要对保真稿整体重渲染，也不要把 HTML 去标签后的文字假装成可逆 Markdown。向用户展示具体改动和当前预览，正文与 HTML 不一致时先解决，不擅自用旧正文重新生成。

## 3. 原地更新

先按 [推送指南](push-governance.md) 核对当前产物与本次上传确认；HTML 参数必须是相对文章目录的文件路径，不能传绝对路径。执行参数以本版 `--help` 为准：

```text
python "<SKILL_DIR>/scripts/draft_sync_guarded.py" update --article-dir "<ARTICLE_DIR>" --html "previews/<已确认主题>.html" --approve-upload
```

入口必须存在拉回基线，并在写回前再次读取后台比对。发生冲突就保存快照、停止写入，先合并；不能把刚拉到的新后台版本直接当作已审阅基线来绕过冲突。更新前执行残留与质量检查，确认图片和修改文件均在文章目录内、哈希仍是已确认版本。评论和来源链接等后台元数据沿用原值；标题、作者及明确提供的摘要按用户确认的 article.md 更新，因此修改前也要核对这些字段。

## 4. 如实回报结果

取得成功响应后保存记录，再回拉核对。未知网络结果保留阻塞标记，不能自动重试。基础回验通过仍不能证明封面身份、图片顺序和实际排版；视觉核对完成后才可说明这些项目通过。更换主题或改动用户后台排版前说明影响，正式发表仍由用户在后台完成。

## 常见故障索引

- **本地缺基线**：先 pull，再基于快照修改；不是删除状态重试。
- **后台版本变化**：拉回并比较，保留双方改动；不自动覆盖。
- **中文接口数据异常**：使用 UTF-8 与 JSON 原生中文编码；错误码还需按当前官方文档核对，不能仅凭字数断定原因。
- **认证过期/权限不足**：给出错误类别，用户在官方设置中修复；不回显完整请求 URL 或 token。
- **更新后看起来不同**：基础文本比对不涵盖完整视觉，检查后台和手机预览；不要重复创建草稿“试试看”。
