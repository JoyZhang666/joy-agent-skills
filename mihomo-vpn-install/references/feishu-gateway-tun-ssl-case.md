# TUN 路由与应用 TLS 失败

TUN 可以接管符合其路由配置的流量；进程级 NO_PROXY 只影响应用是否主动使用代理，不能保证最终 IP 流量绕过 TUN。不能把 TUN 开启等同于全部流量必然被接管。

## 核查链条

1. 应用实际错误是解析失败、TCP 失败、TLS EOF，还是业务鉴权失败？
2. 当前加载的主配置与 controller 状态是否启用 TUN？不要从 provider 缓存中的 `tun` 字段推断主配置已启用。
3. 对目标请求关联时间窗，检查实际命中规则与出站路径；日志无记录可能是日志级别或流量未进入，不能直接证明 TCP 未建立。
4. 对相同目标做经授权的替代路径对照；GeoIP 或域名规则需要依据本地网络实际验证。

SSL EOF 只是现象，跨境路由、代理链、连接池、协议和远端策略均是候选原因，不能仅凭这一错误判定 TUN 是根因。

## 变更原则

确认误路由后，仅给需要的目标添加已验证的规则，置于相应兜底规则之前。DIRECT 和 PROXY 都不应成为所有服务的固定答案。

备份并校验主配置，经授权应用后回读规则和运行状态；原应用是否需要重连或重启取决于其实际恢复情况，不自动重启所有网关。

验证包括目标 TLS、应用连接和业务结果。关闭 TUN 的另一条路径见[回归 SOP](tun-disable-regression-sop.md)；如果根因是应用指向旧代理，见[Privoxy 案例](feishu-actually-privoxy-chain.md)。
