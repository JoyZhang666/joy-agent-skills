# 关闭 TUN：五步回归

关闭 TUN 不一定停止 mihomo 的显式 HTTP/SOCKS 监听，但依赖透明代理或特定 DNS 路由的应用可能断连。不能承诺“所有应用不受影响”。

## 1. 保存基线与恢复路径

在私有目录备份磁盘主配置，记录相关运行字段、路由、监听与应用基线。GET 配置快照不一定包含完整 DNS 或 provider 配置，不能单独替代磁盘备份。

## 2. 应用最小变更

获得关闭 TUN 的授权后，按当前版本支持的字段更新 `tun.enable`，需要时协调 dns-hijack、auto-route；不顺手更换 TUN stack。运行状态与磁盘持久配置的区别必须说明。

API 请求应绕过环境代理并保留所需认证；不在命令或教程中嵌入真实 controller 密钥。PATCH 和 PUT 用途不同，见[官方 API](https://wiki.metacubex.one/api/)。

## 3. 回读与差异

检查 HTTP 状态、运行字段及预期差异。没有变化时停止并分析请求、版本和权限；不要无条件重复请求。原本已为 false 的字段不需要为了产生 diff 再改一次。

## 4. 核查系统与连接

检查 TUN 接管路径是否按预期退出，相关路由与 DNS 是否正确，显式代理监听是否仍在。接口保留与否取决于实现，不能仅凭某个名字消失就判成功。

## 5. 应用验证与回滚

对原有的关键业务逐一验证 DNS、TLS、鉴权及实际结果。读取鉴权响应时只保留成功状态和错误类别，不输出 token；对外发送消息须有单独的发送授权。

记录变更时间与错误增量，结合对照判断因果。达到已约定回滚条件时，恢复准确的旧字段和配置，再验证；不能把所有旧状态假定为 `enable=true`、`auto-route=true` 或固定 stack。
