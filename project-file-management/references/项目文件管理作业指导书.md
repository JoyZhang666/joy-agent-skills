## 1. 目的、适用范围与成功标准

本方法把散落的文件组织为能够定位、理解、继续处理、验证和恢复的项目资产。适用于一个工作区内的多个 Agent 项目，也适用于单项目工作区。它管理文件与证据，不代替业务判断、平台权限或专业验收。

成功标准：

- 新接手者从入口文档能找到目标、原件、当前稿、已确认成果和下一步，不依赖原聊天。
- 同一个事实有明确权威来源：路径看登记，进度看 STATUS，发布看版本清单；发现冲突先复核，不凭“看起来最新”选择文件。
- 已验收成果可按版本定位；交付包换目录后仍能阅读，必要资源不依赖原机器。
- 改名、迁移和清理有准确清单、验证证据与保留边界，不损坏原件和历史成果。

默认采用“顶层按阶段、阶段内按项目”的目录模式与版本清单。已有 Git、团队规范或稳定目录时先评估兼容，不为了形式统一重建一切。目录与文档按需建立；小任务可简化过程文档，但仍要说明输入、输出和验证情况。

## 2. 文件职责与阅读顺序

| 文件 | 回答的问题 | 权威内容 | 何时更新 |
|---|---|---|---|
| 根 AGENTS.md | Agent 应遵守什么规则？ | 通用行为、边界、启动与交接要求 | 规则和环境正式变化时 |
| 根 README.md | 工作区如何使用？ | 总体介绍、主要入口、快速开始 | 入口和使用方式变化时 |
| 根 PROJECTS.md | 有哪些项目，去哪里？ | project.json 的生成视图 | 登记信息变化后重新生成 |
| 项目 README.md | 这个项目做什么，如何使用？ | 目标、输入、输出、运行与局限 | 范围、入口、运行方法变化时 |
| 项目 project.json | 文件实际在哪里？ | 编号、生命周期、路径与正式版登记 | 路径、状态、发布位置变化时 |
| 项目 STATUS.md | 做到哪一步，如何继续？ | 最近进展、证据、当前文件、下一步、阻塞 | 阶段结束、暂停、交接后 |
| 项目 CHANGELOG.md | 哪些重要内容变了？ | 日期、版本、变化与验收依据 | 有实质变化或发布时 |
| 版本 manifest.json | 这一版包含什么、依据什么？ | 输入、依赖、产物、验证及局限 | 每次建立新版本时 |

**启动顺序**：目标工作区根 AGENTS.md → PROJECTS.md → 项目 README.md、project.json、STATUS.md → 按任务读取规范、RUNBOOK、输入材料。人首次访问可先读根 README；Agent 不应跳过适用规则。

从某个阶段子目录直接开始时，先确认所属工作区并显式读取入口。不假设同级或其他目录的 AGENTS.md 已被平台加载；不把某种平台的自动发现行为当作通用能力。

**检查标准**：三个入口各司其职，关键文件都能被入口定位。**常见误区**：把进度复制到所有 README、索引和聊天摘要中，造成多处状态不一致。

## 3. PROJECTS.md：索引如何指定、生成与使用

### 3.1 设计理由与位置

根目录固定使用 `PROJECTS.md`，文件名大小写保持一致。在根 README 与 AGENTS 中明确指向它，使人和 Agent 都有稳定导航入口。项目多时，先看小表定位，再按需阅读目标项目，减少无关信息加载。

索引不是数据库，也不是工作日志。它只展示项目名称、生命周期与正式成果入口；路径及状态从各项目 `project.json` 生成，避免同时手工维护两套记录。

### 3.2 表格框架

| 项目 | 状态 | 最新正式版 |
|---|---|---|
| 示例项目 · 进入项目 README | 进行中 | 尚无已确认正式版；见项目入口 |

实际可运行示例见 [PROJECTS.md](../assets/example-workspace/PROJECTS.md)。无正式版时明确显示未知状态，不能用“最新版”替代未验收草稿。

### 3.3 操作步骤

1. 在 `01_projects/<project-id>/project.json` 建立或修改登记，实际路径先存在再登记。
2. 新建项目时至少备齐 README、project.json、STATUS、CHANGELOG；根入口也需存在。
3. 显式指定根目录，运行工具的 `index` 命令。
4. 阅读生成表格，运行 `audit`，并实际打开项目入口及正式版入口。
5. 登记状态、标题或发布入口变化后重新生成；仅修改某份工作稿正文通常无需刷新索引。

### 3.4 心得与误区

- project-id 稳定，显示名称可调整。标题修改不应连带改变全部目录。
- STATUS 写详细进展；生命周期只有 active、paused、completed、archived 四种。两者并存，各负责不同粒度。
- “生成索引”不是“扫描所有文件并猜测项目”。未登记文件须先确认归属，不能默默归入同名项目。
- 工具生成的索引带所有权标记；遇到既有手工索引时先停止覆盖。保留原索引，比较内容并形成接入方案，经确认后再替换。
- 当表格无法满足筛选需求时，再评估扩展；不要提前引入复杂平台或重复状态库。

## 4. README.md：让人和 Agent 都能接手

### 4.1 工作区 README

面向第一次进入工作区的人，保持简短：工作区用途、规则入口、项目索引、方法规范、模板位置、开始与恢复项目的顺序。它不承载每个项目的详细状态，也不混入私人身份与业务故事。

模板：[工作区 README](../assets/templates/workspace/README.md)。复制时填写工作区用途，校正链接；不需要的可选入口删除后再交付。

### 4.2 项目 README

应能回答六件事：目标与不做什么；输入来源与限制；当前可用成果在哪里；如何运行或阅读；如何验证；有哪些局限。链接到 STATUS、登记和 CHANGELOG，避免复制易变的完整状态。

模板：[项目 README](../assets/templates/project/README.md)。段落必须包含有意义的内容，例如“当前没有验收通过的正式版”比只写“待完善”更适合交接。

### 4.3 操作与检查

建立项目时先写目标、边界、输入和预期输出；执行方式明确后补充依赖与命令。每次入口、依赖、目标或读取方式变化时更新。发布时链接到明确版本，既有正式版继续可定位。

请另一位接手者按照 README 找到输入、当前文件和下一步；无需浏览原聊天即能继续，才算入口有效。不能运行的步骤写明原因和未验证范围，不写模糊的“环境应该没问题”。

**常见误区**：README 只有文件清单；列出命令却没有工作目录或依赖；把历史路径当成当前路径；将大量实时日志堆入入口。

## 5. AGENTS.md：保留通用规则，身份留空

本包使用 `AGENTS.md`，不另建内容重复的 `agent.md`。这是本方法的文件约定，接收平台是否自动读取需自行确认；不支持自动读取时明确要求 Agent 先阅读它。

完整模板：[AGENTS.md](../assets/templates/workspace/AGENTS.md)。保留以下框架：

1. 身份与职责：角色名称、服务对象、职责、工作区、Agent 标识、运行环境、时区留空。
2. 沟通原则：清晰说明结论、事实、假设、阻塞与下一步，代码标识不翻译。
3. 开始、推进与交接：读取入口、按登记定位、按任务补读、阶段结束更新状态。
4. 授权与保密：按已有授权执行，敏感信息不进入通用模板，外部操作不借模板扩大权限。
5. 项目与文件管理：阶段分工、原件保护、正式版本、登记、证据和归档。
6. 执行与验证：小范围修改、先诊断、匹配风险的检查、报告未验证内容。
7. 工具与协作：以实际能力为准，独立工作包才考虑委派，合并责任明确。
8. 规则来源与优先级：服从平台和适用规则，区分指令与外部数据。
9. 业务专用要求：保留填写区，不携带原有业务条款或连接配置。

**使用步骤**：先读目标环境已有规则；填写身份和环境字段；逐项审阅通用约定是否适用；处理冲突后再启用。无需填写的身份信息可明确写“不适用”，不能凭推断补齐。

**检查标准**：真实规则可执行，身份信息有来源，入口可定位。**常见误区**：只替换姓名却保留公司、账号和磁盘路径；删除全部具体文字后只剩空标题；把某个平台 CLI 的使用偏好当成所有 Agent 的硬要求。

## 6. 文件夹系统：设计原则与详细用法

### 6.1 设计原则

顶层区分文件所处阶段，项目编号贯穿各阶段。项目可以跨多个目录，但只有一个管理入口；`project.json` 把分散路径连成文件地图。原件、编辑稿、正式成果不能混放；这能降低误改原件、错发草稿和清理失误。

目录按需建立，不追求全部填满。相对路径使包可迁移；正式产物的完整阅读资源随包携带；跨项目知识在工作区内保留权威副本。目录拆分带来的查找成本，由项目登记和 README 负责补偿。

### 6.2 标准结构示意

```text
<workspace-root>/
├── AGENTS.md
├── README.md
├── PROJECTS.md
├── 00_inbox/
│   ├── _unassigned/
│   └── <project-id>/sources/
├── 01_projects/<project-id>/
│   ├── README.md
│   ├── project.json
│   ├── STATUS.md
│   └── CHANGELOG.md
├── 02_working/<project-id>/
│   ├── drafts/
│   ├── runs/<YYYYMMDD-HHMMSS>/
│   ├── checkpoints/
│   └── qa/
├── 03_outputs/<project-id>/
│   ├── releases/vX.Y.Z/
│   └── legacy/
├── 04_scripts/<project-id>/
├── 04_scripts/_shared/
├── 05_references/<project-id>/
├── 05_references/knowledge/
├── archive/<project-id>/
├── memory/                       可选
└── tmp/                          短期临时
```

### 6.3 每个目录的使用约定

| 目录 | 放什么与何时使用 | 保留与流转 | 常见误区 |
|---|---|---|---|
| `00_inbox/_unassigned` | 新收到、尚未确认项目归属的输入 | 确认归属后按授权移动并登记；不长期堆积 | 依据相似名称自动认领 |
| `00_inbox/<id>/sources` | 原始文件、来源记录、接收说明 | 保留原件；转换、翻译、提取结果进入 working | 用处理结果覆盖原件 |
| `01_projects/<id>` | 管理入口、登记、状态、决策、风险、交接 | 随项目持续维护；归档后仍应可定位 | 存放所有大体积产物 |
| `02_working/<id>/drafts` | 正在编辑的可变草稿 | 稳定文件名；验收后发布一个独立版本 | 每次编辑复制“最终版2” |
| `02_working/<id>/runs/<时间>` | 一次执行的输入选择、过程输出和日志 | 有复现价值的保留；可再生无引用文件可清理 | 不同并行任务写同一路径 |
| `02_working/<id>/checkpoints` | 评审、交接、重大决策的必要快照 | 保留关键节点，记录用途 | 每次保存整包重复快照 |
| `02_working/<id>/qa` | 测试样例、验证结果、路径映射和检查清单 | 保留支撑结论的证据；临时测试副本验证后清理 | 只保留一句“通过” |
| `03_outputs/<id>/releases/vX.Y.Z` | 已确认的正式交付、资源与清单 | 不覆盖；修订新建版本；旧版仍可读取 | 将待验收草稿标作正式成果 |
| `03_outputs/<id>/legacy` | 版本、来源或验收状态不明的历史成果 | 保留原编号，调查后记录结论 | 补造语义化版本和验收事实 |
| `04_scripts/<id>` | 项目脚本、技能源码、依赖及运行说明 | 保留重现成果所需版本；依赖需明确 | 凭证硬编码，依赖只存在聊天中 |
| `04_scripts/_shared` | 已经确认跨项目复用的工具 | 修改前检查使用方；避免存放私人输入 | 为一次性脚本提前设计通用框架 |
| `05_references/<id>` | 外部规范、背景材料、恢复说明 | 记录来源、适用版本和使用限制 | 把参考资料误当作实际项目输入 |
| `05_references/knowledge` | 跨项目长期知识权威副本 | 工作区内引用；独立交付时附所需资源 | 去重破坏原件证据或离线阅读 |
| `archive/<id>` | 结项后可独立阅读和恢复的归档包 | 保留 README、成果、必要输入、依赖和校验 | 误以为归档等于异地备份 |
| `memory` | 经允许维护的偏好与历史线索 | 遵守宿主记忆策略；当前项目事实以文档为准 | 自动把客户信息写入长期记忆 |
| `tmp` | 有明确短期用途的临时产物 | 完成本次用途且无引用后清理 | 当成长期项目资料库 |

### 6.4 容易混淆的边界

- sources 是收到的原件；references 是帮助理解与工作的资料。同一文件兼具两种用途时登记用途，优先保留来源证据，不按扩展名决定归属。
- drafts 是持续修改的稿；runs 是一次执行的记录；checkpoints 是有理由保留的节点；qa 是支撑结论的证据。
- releases 是发布历史；archive 是长期恢复组织方式。归档无需将全部历史重复复制，可用清晰入口或独立包，但必须说明实际保留位置。
- 项目长期不推进使用 paused；业务目标完成才使用 completed；按归档策略完成整理后使用 archived。目录检查或迁移成功不应自动改变业务状态。

## 7. 项目登记与模板使用

### 7.1 project.json 字段

| 字段 | 约定 |
|---|---|
| `id` | 稳定小写英文、数字与短横线；唯一，与 `01_projects` 下登记目录名一致 |
| `title` | 人可读名称，可中文，不兼任文件路径 |
| `lifecycle` | active、paused、completed、archived |
| `stage_paths` | 逻辑阶段到实际目录的映射；至少有 `01_projects`，指向当前登记目录 |
| `latest_release` | 已确认正式版目录的工作区相对路径；尚无正式版写 null |
| `artifacts` | 需要直接定位的重要成果文件的相对路径字符串数组；可空 |
| `updated` | 最近一次修改登记的日期，YYYY-MM-DD |

所有路径使用 `/`，禁止绝对盘符、`..` 或越出根目录的链接。只登记真实存在且需要使用的目录；新增阶段时先创建再登记。已有项目可将阶段映射到根目录内的既有位置，工具不会强制要求所有内容搬到标准阶段路径；管理登记入口仍固定在 `01_projects/<id>`。

项目生命周期、文档审阅状态和交付版本是不同维度。推荐文档状态使用 draft、in-review、accepted、superseded；它不改变 lifecycle 的含义。

### 7.2 模板清单与填写规则

| 模板 | 使用时机 |
|---|---|
| [工作区模板目录](../assets/templates/workspace/) | 新建工作区或审阅现有入口规则 |
| [项目模板目录](../assets/templates/project/) | 每个登记项目建立四个基础文件 |
| [可选模板目录](../assets/templates/optional/) | 长程计划、决策、风险、运行说明或发布时按需使用 |

模板出现 `<project-id>`、`【待填写】` 等提示是有意留白。复制后逐项填写、删除无用区块并校正相对链接；不要对整个工作区做未经检查的全文替换。JSON 模板是可解析的结构示例，示例 id 和日期也必须替换。文档头建议包含 doc_id、version、status、updated、change_summary；原件不加头，元数据另存来源清单。

## 8. 从新建到交接的操作步骤

| 阶段 | 输入与操作 | 输出与完成标准 |
|---|---|---|
| 新建工作区 | 确认根目录、适用规则与用途；从模板建立根入口和 `01_projects` | 入口可读；身份信息填写或标注不适用；没有覆盖既有规则 |
| 新建项目 | 选稳定 id；创建四个基础文件；按需建阶段目录并登记 | index、audit 通过；目标、输入和预期成果清楚 |
| 接收输入 | 核实归属与来源；保留原文件名与内容；必要时记录 SHA-256 | 输入可定位，来源与限制明确；未归属文件单列 |
| 日常推进 | 读取项目入口与状态；使用 drafts 或新 run；只改任务范围 | 当前文件、变化与验证证据可追踪 |
| 暂停交接 | 更新 STATUS，记录准确文件、已完成、下一步、阻塞、依赖与负责人 | 新接手者不读原聊天也能继续；没有虚报验证 |
| 实质变更 | 更新相关 README、登记或 CHANGELOG；状态改变后刷新索引 | 入口、登记、索引和交接相互一致 |

长程任务按需使用 PLAN、DECISIONS、RISKS、RUNBOOK。决策记录写问题、选项、结论、理由、影响和日期；运行说明写前置条件、命令、预期结果、失败诊断及恢复入口。没有可运行步骤的纯阅读项目不必硬写脚本。

**示例走读**：打开[示例工作区](../assets/example-workspace/README.md)，顺着 PROJECTS 进入 example-project，查看 sources 中的虚构需求、drafts 中的编辑稿、STATUS 中的模拟交接、releases 中的演示成果。已发布演示版与继续修改的工作稿同时存在；latest_release 仍指向已确认的演示版。这说明“项目进行中”与“有一个正式版本”并不冲突。

## 9. 验收、版本发布与归档

### 9.1 版本规则

使用 `v主版本.次版本.修订号`：不兼容的结构或接口变化升主版本，新增内容或能力升次版本，纠错升修订号。未验收稿使用 v0.x.y 并留在 working；首个正式版通常 v1.0.0。既有历史编号不强制转换。

编辑稿使用稳定文件名；正式版由版本目录区分，不再复制“latest”目录。需要便捷访问时更新登记链接。本技能包采用统一发布版本：发布目录、技能入口、指导书、完整 ZIP 文件名和 manifest 中的 version、asset_version 必须一致。每次交付按变更性质升版，不覆盖旧发布；版本说明纠错升修订号。assets 中的模板初始版本与虚构案例版本属于教学内容，不跟随包版本替换。

### 9.2 发布步骤与清单

1. 明确本次验收对象和标准；完成与成果类型相称的内容、布局或功能检查。
2. 准备独立的新版本目录；关联输入、脚本和依赖，附必要阅读资源。
3. 验证相对链接、内容完整性与已知局限；清单记录执行过的检查及结果。
4. 生成 manifest.json 和 checksums.sha256，复核后冻结该版本。
5. 更新 latest_release、README 必要入口、CHANGELOG、STATUS，再生成索引。

manifest 的 files 列出有效载荷文件的相对路径、SHA-256 和适用文档版本；不把 manifest 自己放入自己的哈希记录，避免循环。checksums 可列出 manifest 与有效载荷，但不记录自己。示例发布目录演示了这种关系。校验只能证明文件与指定摘要一致，不能证明来源可信或业务正确。

### 9.3 归档与清理

结项先确认成果、关键输入、脚本、依赖、决策和未决问题的保留位置。归档入口应解释如何阅读和恢复；存在无法重建的外部依赖时如实记录。新路径完成阅读或重建检查后，才处理确认可再生且无引用的过程副本。

清理候选清单至少包括准确路径、大小、用途、保留位置及删除理由；按已授权批次执行，不顺带处理清单外文件。发现正在写入、未知归属或哈希变化时暂停该项并保留。既有授权不反复索取；归档、打包和本地验收不自动授权对外发布。

## 10. 既有项目接入与迁移

**设计理由**：优先让文件可定位、规则可理解，再考虑目录整齐。接入管理并不必然要求迁移全部资料。

1. **盘点**：读取现有 AGENTS、README、索引、版本与依赖；记录实际结构、关键链接和保护对象。把已确认事实与未知状态分开。
2. **映射**：建立现有路径、逻辑阶段、拟保留/调整方式及理由的表。可先创建标准管理入口，用 stage_paths 指向现有目录；根目录外资料先评估纳入边界，工具不接受越界登记。
3. **处理差异**：现有规则与模板逐条比较；保留有效规则，提出必要补充；手工 PROJECTS 先保留再转换。已有 Git 保持不变，版本清单用于交付追溯而非替代提交历史。
4. **形成批次**：确需迁移时，逐文件列出原路径、目标路径、大小、SHA-256、用途、引用和保留策略；先展示范围再按明确授权执行。
5. **复制与验证**：先复制，验证哈希、阅读入口、依赖与可运行样例；原件原则上字节不变，管理说明和脚本必要路径变化单独记录。
6. **完成切换**：更新登记与入口，重建索引；按批准清单逐项复核后处理旧副本。中断后根据实际完成记录续做，不重新猜测已处理项。
7. **交接**：STATUS 写明迁移验证与业务验收分别达到什么程度。旧报告路径可作为历史证据保留，并给出新旧路径映射。

**检查标准**：保护对象保真、登记位置正确、入口和依赖可用、未验证功能明确、范围外文件未改。**常见误区**：先批量搬动再修链接；发现旧成果就自动补版本；用目录校验通过宣称全部业务可用。

本包工具只辅助索引与检查，迁移清单、复制和删除由接收方依批准范围执行。

## 11. 工具使用与检查边界

需要 Python 3.10 或以上及标准库。脚本可在技能包原位置调用，无需安装；路径包含空格时加引号。先把下面尖括号参数替换为实际位置：

```text
python "<skill-directory>/scripts/workspace_admin.py" audit --root "<workspace-root>"
python "<skill-directory>/scripts/workspace_admin.py" index --root "<workspace-root>"
```

首次工作区没有 PROJECTS 时，audit 会报告缺失；根入口和项目登记准备好后运行 index，再 audit。空工作区允许零项目，`01_projects` 仍需存在。

| 命令 | 实际行为 | 不做什么 |
|---|---|---|
| index | 先验证根入口和所有登记；仅写 PROJECTS；按 id 排序；相同内容不重写 | 不猜测项目归属，不覆盖未带工具标记的索引 |
| audit | 只读检查入口、基础文档、字段、编号、目录、成果入口和索引一致性 | 不更改状态、不遍历所有正文链接、不证明发布哈希或业务内容正确 |

两个命令均输出 `passed`、`projects`、`errors`。projects 是有效登记数；有错误时不能当成全部项目数量。退出码 0 为通过，1 为失败，2 为命令参数错误。脚本会拒绝绝对路径、`..` 与符号链接越界；它不是隔离并发恶意进程的安全沙箱，应在稳定的本地目录操作。

工具要求 `01_projects/<id>/project.json` 作为登记发现入口，且该管理目录含四份基础文件；其余 stage_paths 可指向工作区内实际目录。latest_release 只检查目录存在，不替你判断它是否完成验收，也不强制改造历史版本名。

| 故障 | 处理方法 |
|---|---|
| 缺少基础文件或登记目录 | 核对项目真实情况后补齐，不生成虚假内容 |
| 重复编号、目录名不匹配 | 确认正确归属与稳定 id，再按授权改动 |
| 路径无效、目录不存在 | 确认根目录与实际位置，修正登记；不要创建空目录掩盖错误 |
| 索引不一致 | 核对登记修改正确后运行 index |
| 既有手工索引 | 保留原件，比较并确认转换方案；不要直接添加标记绕过保护 |
| 无正式版 | latest_release 写 null，artifacts 可空，正常通过 |
| 发布入口存在但内容有误 | 使用成果专用验收方法；本工具不能诊断业务质量 |

## 12. 经验复盘、验收清单与复用方式

### 12.1 可复用心得

- 规范的价值在于下一步能继续，而不在于目录看起来完整。缺少交接证据时，多写几个模板也解决不了问题。
- 把易变与稳定内容分开：STATUS 高频更新，README 维护使用方式，AGENTS 维护长期规则，索引负责导航。
- 登记和索引避免双写；原件与工作稿隔离；正式版与历史未知稿隔离。边界清楚比复杂命名更有效。
- 历史记忆用于提示，当前路径和状态需从登记与实际文件验证。迁移完成、语法检查通过、模拟运行成功与业务验收是不同结论。
- 先用最低必要结构；真实复用后再抽取共享工具。平台安装、自动加载、云同步和外部发布不属于目录方法本身。

### 12.2 验收清单

- [ ] 已明确根目录、适用规则和 project-id；身份字段已填写或标注不适用。
- [ ] 根入口、项目四份基础文件可用；登记、索引、README 与 STATUS 不冲突。
- [ ] 原件、当前稿、正式版与历史未知稿位置清楚；真实链接可打开。
- [ ] 交接提供已做事项、证据、当前文件、下一步、阻塞与依赖。
- [ ] 发布带输入与依赖说明、局限、清单和哈希；未覆盖旧正式版。
- [ ] 可分享资产没有真实客户、身份、账号、凭证、机器路径或私人链接。
- [ ] 独立包换目录后能阅读；业务功能有独立验收记录或明确标注未验证。
- [ ] 接入或清理只处理已确认范围，保留历史证据和恢复入口。

### 12.3 三种交付方式的选择

| 形式 | 优势 | 局限 |
|---|---|---|
| 单份作业指导书 | 易读、易审阅、适合收藏 | 模板需提取，自动执行一致性依赖接收方 |
| 纯 Skill 包 | Agent 调用集中，可携带工具 | 不支持技能的平台需手动读取，长流程不便系统阅读 |
| 指导书＋模板＋薄层 Skill＋工具 | 同一方法同时面向人和 Agent，可按需调用 | 需要保持内部引用、模板与工具一致 |

本包采用第三种。只阅读时从本文开始；复用模板时打开 assets/templates；学习时看虚构 example-workspace；支持技能的平台可按其当前规则配置 skill 目录，不支持的平台显式读取 SKILL.md 和本文即可。本包交付不等于已经安装，也不保证所有平台会自动发现技能。

例如可向接收方 Agent 发出：

> 阅读本包 SKILL.md 和对应指导书章节。目标工作区由我指定。先检查现有规则和目录；若为新项目，按模板建立最小管理入口；若为既有项目，先给出现状与目标映射。不要将虚构示例作为实际资料，也不要覆盖现有规则或未确认的文件。

维护时修改这一份正文，并同步受影响模板、脚本与验收用例。包版本由新发布目录区分；不要分叉出另一份内容相同但独立维护的“简版规范”。

分享时只打包本技能目录内的 SKILL.md、references、assets 和 scripts。不要附带实际工作区规则、已填写的身份模板、项目登记、原始输入、运行日志、隐藏配置或凭证；模板投入使用后产生的数据需要重新审核。压缩包使用相对路径，清空注释及额外元数据，文件时间使用统一占位值而非本机编辑时间。
